## CAPA A — Principios metodológicos cerrados

### P-01 — Convención de signos

| Campo | Contenido |
|---|---|
| Decisión | Se distinguen cuatro capas para cualquier cuenta financiera: **(1) signo reportado/original** (tal como aparece en el documento fuente); **(2) convención de presentación** (débito/crédito, paréntesis para negativos, notación contable local); **(3) transformación técnica** (cualquier operación aplicada para llevarlo a una convención canónica); **(4) valor económico usado en el cálculo**. La regla base es: **preservar el signo observado y su procedencia (provenance)** — no se aplica `Math.abs()` ni ninguna otra normalización de signo como regla universal. Cuando una fuente usa una convención distinta (débito/crédito, gasto reportado en negativo, nota crédito), la transformación a la convención canónica de Velarix debe ser **explícita, documentada, reversible y trazable** — nunca una operación ciega aplicada a todo un objeto de datos. |
| Fundamento | Ocultar el signo original destruye información económica real: un patrimonio negativo, una reversión de gasto o una nota crédito tienen un significado financiero distinto de "positivo con signo invertido por convención de captura". Una transformación no documentada no puede auditarse ni revertirse si resulta incorrecta para un caso específico. |
| Fuente | Principio de integridad y trazabilidad de datos de entrada — IVS 104 *Data and Inputs* (IVSC, vigente desde 31 enero 2025) exige que los inputs de una valoración sean sustanciados y verificables; una transformación de signo no documentada rompe esa verificabilidad. No requiere una fuente externa adicional para el principio en sí — es consistencia interna de auditoría, no una elección entre alternativas metodológicas legítimas. |
| Alternativas consideradas | (a) Mantener `Math.abs()` universal (comportamiento actual) — rechazada: oculta información económica real, ya contradice una decisión previa del fundador para `equity` (Decisión 6, Bloque 1B-M). (b) Normalizar signo solo para el balance, dejar el estado de resultados sin tocar — rechazada por inconsistente: el mismo riesgo de ocultar una nota crédito o reversión aplica a ambos estados. (c) Preservar signo + provenance, con transformación explícita y auditable cuando haga falta una convención canónica — **aceptada**. |
| Por qué se rechazaron las alternativas | (a) fue exactamente el patrón que la reorientación boutique-expert-led identificó como el error central (caso Tecnoglass, patrimonio negativo enmascarado). (b) resuelve el síntoma más visible (equity) pero deja el mismo riesgo latente en revenue/COGS/OPEX/D&A/interest expense, que `01-scope-surgery.md §7.1` ya registró como hallazgo sin diagnosticar. |
| Implicación para código futuro | `canonical-input-normalization.ts` deja de aplicar `Math.abs()` ciego por campo; cualquier transformación de signo pasa a requerir una razón explícita registrada. Esto no se implementa en este bloque (restricción explícita: no modificar código todavía). **Alcance**: el caso de `equity` es **`required for Alpina`** — ya contradice una decisión aprobada (Decisión 6) y afecta directamente ROE/beta/WACC de cualquier caso real. Para revenue/COGS/OPEX/D&A/interest expense, el alcance es **`can be handled manually/through existing structures`** mientras no haya evidencia de un valor negativo legítimo en los datos de Alpina (verificación manual del caso primero) — no se justifica reescribir toda la normalización antes de confirmar que Alpina lo necesita. |
| Test financiero requerido | Cuando se implemente: un test por campo que verifique que el signo observado se preserva exactamente en `structured_input`, y que cualquier transformación aplicada quede registrada junto con su justificación — no un test que simplemente verifique "el resultado es positivo". |
| Pregunta de entrevista | "¿Cómo garantizan que no están ocultando un signo económicamente significativo al normalizar los datos de Alpina?" |
| Respuesta defendible de Nicolás | "No aplicamos ninguna transformación de signo sin verificar primero contra el documento fuente qué significa ese signo — preservamos el original y documentamos cualquier ajuste, de forma reversible." |

### P-02 — Estructura de capital: reabierta, no preservada por inercia

| Campo | Contenido |
|---|---|
| Decisión | **Se reabre la Decisión 2 del Bloque 1B-M — no se preserva por inercia, pero tampoco se reemplaza por una nueva regla universal.** El principio de cierre es de **consistencia**, no de una fuente única obligatoria: los pesos de estructura de capital del WACC deben usar **valores de mercado/económicos, no valores contables (book value)**, siempre que exista una base razonable para estimarlos — y esos pesos deben ser **internamente consistentes** con el beta usado (apalancado/des-apalancado al mismo nivel de deuda), con el costo de deuda usado, y con la estructura implícita en cualquier otro supuesto del caso. Para una empresa privada, **no existe un valor de mercado observable de su propio equity**, lo que descarta usar el book value propio como si fuera equivalente a un valor de mercado sin más — pero no hay una única alternativa correcta: **(a)** la estructura de mercado promedio de comparables de industria (des-apalancada/re-apalancada) es un **default práctico razonable cuando no existe evidencia mejor sustentada de una estructura objetivo propia** — no porque sea "la" respuesta correcta, sino porque es observable y no depende circularmente del resultado que se está calculando; **(b)** una **estructura objetivo explícita** de la propia empresa (declarada y justificada con evidencia — ej. una política de apalancamiento documentada, un plan de refinanciamiento) puede ser igual o más defendible que el promedio de comparables si existe esa evidencia; **(c)** una **estructura óptima** derivada de un análisis propio (ej. minimización de WACC dentro de un rango de apalancamiento sostenible) es otra alternativa legítima si el caso lo justifica; **(d)** un **proceso iterativo** que resuelve la circularidad (converger equity value y estructura de capital simultáneamente) es técnicamente válido y puede preferirse sobre comparables si se dispone de la capacidad de calcularlo. La estructura contable observada de la propia empresa se conserva siempre como **verificación de sanidad** (sanity check) frente a cualquiera de las cuatro alternativas elegidas — un resultado que se aparta demasiado de la estructura observada sin justificación merece revisión, no aceptación automática. **Lo que no es defendible es usar el book value propio como proxy no cuestionado de un valor de mercado**, ni cualquier elección que deje inconsistencia entre beta, costo de deuda y pesos del WACC. |
| Fundamento | Evitar la circularidad model-output-como-model-input y usar valores de mercado/económicos en vez de un valor contable no confiable son principios estándar de valoración corporativa, generales, no específicos de ningún país. Pero convertir "comparables de industria" en la única respuesta correcta repetiría, en sentido inverso, el mismo error que este bloque busca evitar en otros temas: una regla mecánica aplicada sin verificar primero si existe evidencia case-specific mejor (estructura objetivo propia, análisis de estructura óptima). |
| Fuente | Aswath Damodaran / NYU Stern — tratamiento estándar de estructura de capital para empresas privadas: uso de valores de mercado/económicos sobre book value, el problema de circularidad en el cálculo de WACC cuando el equity value es simultáneamente input y output del modelo, y el uso de comparables de industria des-apalancados/re-apalancados como *uno* de los métodos estándar reconocidos para estimar beta y estructura cuando no hay valor de mercado propio observable (material de valoración de Damodaran sobre estructura de capital objetivo; consultado 2026-08-31). Fecha de la metodología: sin versión fechada única — es la práctica consistente descrita en su material docente y sus notas de valoración vigentes; no excluye explícitamente las alternativas (b)-(d) como igualmente legítimas cuando la evidencia las respalda. |
| Alternativas consideradas | (a) Estructura observada (book value) de la propia empresa como única fuente, sin cuestionamiento (Decisión 2 original) — degradada a verificación de sanidad, no eliminada. (b) Comparables de industria como única regla universal de reemplazo — **rechazada explícitamente**: convertiría un default práctico en una nueva regla mecánica. (c) Cuatro alternativas legítimas (comparables como default práctico, estructura objetivo explícita, estructura óptima, proceso iterativo), cada una válida según la evidencia disponible, con la estructura observada como verificación de sanidad en todos los casos, y exigiendo siempre consistencia beta/costo de deuda/pesos — **aceptada**. |
| Por qué se rechazaron las alternativas | (a) como única fuente ignora tanto el problema de valor contable no representativo como la circularidad. (b) como regla universal cometería el mismo error metodológico que motivó reabrir la Decisión 2: reemplazar una simplificación mecánica por otra, en vez de dejar la elección gobernada por la evidencia del caso. |
| Implicación para código futuro | Ver clasificación de alcance al final de esta fila. **Alcance**: la aplicación de este principio a Alpina (elegir entre comparables/estructura objetivo/óptima/iterativa y calcular los pesos resultantes) **puede resolverse manualmente fuera del motor** (`can be handled manually/through existing structures`) — el cálculo se hace en el análisis del caso y se usa como override informado del WACC, sin requerir que `capital-structure.ts` incorpore una fuente de comparables de industria. Construir un mecanismo general y automatizado de comparables dentro del motor canónico es **`NOT BUILDING`** en este momento — un solo caso (Alpina) no justifica esa infraestructura; se reconsideraría solo si múltiples casos futuros la demandan. El fallback 70/30 hardcoded (`capital-structure.ts:49`) sigue siendo un placeholder provisional documentado, no la metodología objetivo. |
| Test financiero requerido | Cuando se implemente algo en código: verificar que el `equityWeight`/`debtWeight` usado para WACC no dependa circularmente del `equityValue` que ese mismo cálculo produce, y que el beta y el costo de deuda usados sean consistentes con la estructura elegida. Para Alpina, mientras la resolución sea manual, no aplica un test de código — sí debe quedar documentada la consistencia beta/costo de deuda/pesos en el análisis del caso. |
| Pregunta de entrevista | "¿Por qué eligieron [comparables de industria / estructura objetivo / estructura óptima] para Alpina y no simplemente su estructura contable observada?" |
| Respuesta defendible de Nicolás | "Evaluamos si existía evidencia de una estructura objetivo propia mejor sustentada que el promedio de comparables; si no la había, usamos comparables públicos del sector como default práctico — en ambos casos, verificamos que el beta, el costo de deuda y los pesos del WACC fueran consistentes entre sí, y usamos la estructura contable observada de Alpina como verificación de sanidad, no como fuente única." — la elección concreta para Alpina es case-specific (ver C-02). |

### P-03 — Impuesto corporativo: tasas y su uso correcto

| Campo | Contenido |
|---|---|
| Decisión | Se distinguen formalmente cinco conceptos, antes confundidos en un solo "30% fijo": **(1) tasa estatutaria/general (statutory/general rate)** — verificada en fuente primaria: **35%**, tarifa general del sistema ordinario del impuesto de renta para personas jurídicas en Colombia (Art. 240 del Estatuto Tributario, modificado por el Art. 10 de la Ley 2277 de 2022; confirmado directamente en `dian.gov.co/impuestos/sociedades/Paginas/Renta-personas-juridicas.aspx`, cita textual: "la tarifa general del sistema ordinario del 35%"). **(2) tasa marginal** — la tasa aplicable al siguiente peso de utilidad; en el sistema colombiano de renta corporativa (tarifa plana, no por tramos) coincide con la estatutaria (35%) salvo régimen especial o sobretasa sectorial. **(3) tasa efectiva (effective tax rate)** — impuesto realmente pagado/causado sobre utilidad contable, puede diferir de la estatutaria por diferencias temporales, deducciones, créditos, o pérdidas fiscales en uso. **(4) cash tax rate** — impuesto efectivamente pagado en efectivo, relevante para FCFF cuando hay diferencias de tiempo entre impuesto causado e impuesto pagado (impuestos diferidos). **(5) NOLs/pérdidas fiscales compensables** — reducen la tasa efectiva/cash mientras se compensan, sin cambiar la tasa marginal/estatutaria de largo plazo. **Principio de uso**: la tasa marginal/estatutaria (verificar 35% vigente al momento del cálculo, no asumir que se mantiene) es la que corresponde usar en el **valor terminal / estado estable** del DCF, porque en perpetuidad las distorsiones temporales (NOLs, diferencias contable-fiscal) se agotan. Para los **años del horizonte explícito**, la tasa efectiva/cash puede ser menor que la marginal si la empresa tiene pérdidas fiscales u otras compensaciones en uso, convergiendo hacia la marginal a medida que esas compensaciones se agotan. |
| Fundamento | Usar la tasa marginal en el valor terminal evita subestimar sistemáticamente los impuestos de largo plazo por una condición transitoria (NOLs) que no persiste en perpetuidad; usar la tasa efectiva/cash en los años cercanos evita sobreestimar los impuestos reales que la empresa efectivamente paga mientras tiene beneficios fiscales disponibles. |
| Fuente | **(a)** DIAN — `dian.gov.co/impuestos/sociedades/Paginas/Renta-personas-juridicas.aspx`, consultado 2026-08-31: tarifa general 35%, base legal Art. 240 ET modificado por Ley 2277 de 2022. **(b)** Aswath Damodaran / NYU Stern — "More on effective tax rates" (`pages.stern.nyu.edu/~adamodar/New_Home_Page/valquestions/taxrate.htm`, consultado 2026-08-31): "it is critical that the tax rate used in perpetuity to compute the terminal value be the marginal tax rate"; recomienda usar tasa efectiva en los primeros años y converger a la marginal; tratamiento de NOLs: "in the year of the operating loss, the tax rate should be zero... when you use up your net operating losses, your tax rate will converge on the marginal tax rate". |
| Alternativas consideradas | (a) Mantener 30% fijo como referencia general (comportamiento actual) — rechazada: la fuente primaria (DIAN) contradice ese valor para la tarifa general vigente. (b) Reemplazar automáticamente 30% por 35% como nuevo valor fijo único, usado igual en todos los años y para todos los propósitos — rechazada explícitamente por instrucción de este bloque: no distingue tasa marginal/efectiva/cash ni contempla NOLs. (c) Distinguir las cinco tasas y usar cada una en el punto correcto del modelo (marginal en terminal value, efectiva/cash con convergencia en el horizonte explícito) — **aceptada**. |
| Por qué se rechazaron las alternativas | (a) está objetivamente desactualizada o mal descrita frente a la fuente primaria oficial vigente. (b) repetiría el mismo error de fondo que (a) — una sola tasa fija aplicada mecánicamente en todos los contextos — solo que con un número distinto, sin resolver la distinción marginal/efectiva/cash que realmente importa para la precisión del modelo. |
| Implicación para código futuro | `financial-methodology.ts:70-80` (`taxRatePct`) requiere, como mínimo, (1) actualizar el valor de referencia general y su fuente citada correctamente, y (2) en una implementación futura, separar la tasa usada en el valor terminal (marginal) de la tasa usada en el horizonte explícito (efectiva/cash, con posible convergencia) — hoy el motor usa una sola tasa (`taxRate=30`) para ambos propósitos. No se modifica el código en este bloque. **Alcance**: verificar y aplicar la tasa correcta (35%) para Alpina es **`required for Alpina`**, pero puede resolverse **`can be handled manually/through existing structures`** (el valor se calcula/documenta en el análisis del caso y se alimenta al motor existente); separar formalmente marginal/efectiva dentro de `financial-methodology.ts` como estructura de datos general es razonable pero no urgente para un solo caso. |
| Test financiero requerido | Cuando se implemente: test que confirme que el valor terminal usa la tasa marginal/estatutaria vigente (verificada contra fuente primaria en la fecha del cálculo), y que el horizonte explícito puede usar una tasa efectiva/cash distinta si el caso tiene NOLs u otras compensaciones documentadas. |
| Pregunta de entrevista | "¿30% o 35%? ¿Y es la misma tasa que usan para el valor terminal que para el primer año de proyección?" |
| Respuesta defendible de Nicolás | "La tarifa general vigente en Colombia es 35% según Art. 240 del Estatuto Tributario — la verificamos directamente en la DIAN antes de usarla. Para el valor terminal usamos la tasa marginal/estatutaria vigente; si Alpina tiene pérdidas fiscales compensables u otro beneficio específico en los años cercanos, la tasa efectiva de esos años puede ser menor, convergiendo a la marginal — no aplicamos ciegamente el mismo número en todos los años sin verificar la situación fiscal real de Alpina." |

### P-04 — FCFF: realismo del escudo fiscal, EBIT negativo y NOLs

| Campo | Contenido |
|---|---|
| Decisión | Se mantiene la arquitectura `FCFF = EBIT×(1−T) + D&A − CAPEX − ΔNWC` (NOPAT sobre EBIT, sin usar el impuesto clamped-en-EBT que sí aplica a la utilidad neta — ver `02-methodology-reconciliation.md` tema 2, `KEEP`). **Pero se corrige la afirmación de que `EBIT×(1−T)` sin más es siempre correcto, incluso con EBIT negativo — sin reemplazarla por un automatismo distinto igual de mecánico.** `EBIT×(1−T)` es una **presentación algebraica** que asume implícitamente que la empresa puede monetizar el escudo fiscal de forma inmediata y completa. **Principio de cierre**: **solo se reconoce un beneficio fiscal (o su ausencia) cuando existe capacidad legal y económica razonable de utilizarlo** — no una regla fija de "EBIT negativo → T=0". Esa capacidad depende de un conjunto de factores que deben evaluarse, no asumirse en ninguna dirección: **(a)** si existen NOLs u otros créditos fiscales acumulados y su saldo disponible; **(b)** si la jurisdicción permite compensar esa pérdida contra utilidad gravable futura (o, en algunos regímenes, pasada — carryback) y bajo qué límites (plazo, porcentaje máximo compensable por año, tipo de renta); **(c)** si existe utilidad gravable futura razonablemente esperable (propia o, si aplica el régimen, consolidada a nivel de grupo) dentro del plazo legal de compensación — un EBIT negativo puntual en un año, dentro de una empresa que genera utilidad gravable consistente en otros años o entidades del grupo, puede seguir generando un beneficio fiscal realizable, mientras que una pérdida sin ninguna utilidad gravable futura razonablemente esperable no lo genera, independientemente del signo del EBIT en ese año específico. Tanto asumir automáticamente un beneficio fiscal inmediato con EBIT negativo, como asumir automáticamente `T=0` sin verificar si existe capacidad real de uso futuro, son dos versiones del mismo error: sustituir el análisis de realización por una regla mecánica. |
| Fundamento | Aplicar `EBIT×(1−T)` mecánicamente con EBIT negativo puede sobreestimar el flujo de caja real si la pérdida no puede monetizarse; pero fijar `T=0` mecánicamente para cualquier EBIT negativo puede subestimarlo si la pérdida sí es realizable (grupo con utilidad gravable consolidada, carryback disponible, u otra vía). Ninguna de las dos reglas fijas sustituye la verificación real de capacidad de uso. |
| Fuente | Aswath Damodaran / NYU Stern — "More on effective tax rates" (misma fuente que P-03): reconoce que la tasa efectiva converge hacia la marginal a medida que se agotan las pérdidas acumuladas, consistente con el principio de realización aquí cerrado, aunque la fuente en sí no cubre las reglas jurisdiccionales específicas (carryback, límites de compensación, consolidación fiscal de grupo) — esas reglas son normativa tributaria local (DIAN/Estatuto Tributario para Colombia, ver P-03), no un principio de valoración generalizable, y deben verificarse caso por caso. |
| Alternativas consideradas | (a) Mantener `EBIT×(1−T)` sin excepción, incluso con EBIT negativo — rechazada: puede reconocer un beneficio fiscal que económicamente no puede realizarse. (b) Reemplazarla por la regla fija `EBIT negativo → T=0` sin verificar capacidad de uso futuro — **rechazada explícitamente por instrucción de este bloque**: es un automatismo distinto, no un análisis de realización; ignora casos legítimos donde la pérdida sí es realizable (consolidación de grupo, carryback, utilidad gravable futura razonable). (c) Principio de realización caso por caso (capacidad legal y económica razonable de uso, verificando NOLs/jurisdicción/utilidad gravable futura) — **aceptada**. |
| Por qué se rechazaron las alternativas | (a) es la afirmación que este mismo bloque pidió explícitamente revisar. (b) sustituiría un automatismo por otro — exactamente lo que este bloque pidió evitar; además es empíricamente incorrecta en casos donde la realización sí es razonable a pesar de un EBIT negativo puntual. |
| Implicación para código futuro | `canonical-financial-engine.ts:154` (`nopat = ebit − ebit×taxRate`, sin clamp) no se modifica en este bloque. **Alcance**: si Alpina presenta EBIT negativo en el histórico o la proyección, o tiene NOLs, evaluar su realización es **`required for Alpina`** — pero la evaluación en sí **`can be handled manually/through existing structures`** (análisis del caso documentado en el Expediente, aplicado como ajuste manual del NOPAT/FCFF de esos años), sin requerir una variable de estado de NOLs dentro del motor. Si Alpina no presenta EBIT negativo ni NOLs, este principio queda **`NOT BUILDING`** para este caso — no hay nada que evaluar ni codificar. Construir una lógica automática de arrastre de NOLs en el motor canónico solo se justificaría con evidencia de varios casos reales que la necesiten. |
| Test financiero requerido | Si Alpina lo requiere: verificación manual (no de código) de que el ajuste de NOPAT/FCFF de cualquier año con EBIT negativo está respaldado por un análisis explícito de capacidad de realización (NOLs, jurisdicción, utilidad gravable futura), no por una regla automática en ninguna dirección. |
| Pregunta de entrevista | "Si Alpina tuviera un año de EBIT negativo en la proyección, ¿su modelo le estaría dando un beneficio fiscal automático por esa pérdida, o automáticamente ninguno?" |
| Respuesta defendible de Nicolás | "Ninguna de las dos automáticamente — evaluamos si existe capacidad legal y económica real de usar esa pérdida (NOLs disponibles, reglas de compensación aplicables, utilidad gravable futura razonable) antes de decidir el efecto fiscal de ese año, en vez de aplicar una regla fija en cualquier dirección." |

### P-05 — WACC y consistencia de moneda/inflación

| Campo | Contenido |
|---|---|
| Decisión | Se cierran cuatro principios generales de **metodología**, separados explícitamente de los **datos fechados** que los alimentan (ver nota al final de esta fila). **(1) Consistencia flujo-tasa**: flujos de caja nominales en COP deben descontarse con una tasa de descuento nominal en COP; flujos reales (ajustados por inflación) requieren una tasa real. **(2) Riesgo de usar el rendimiento soberano colombiano completo como "risk-free"**: el rendimiento de un TES colombiano incorpora el riesgo de default soberano de Colombia — usarlo directamente como "tasa libre de riesgo" y **además** sumar una prima de riesgo país (CRP) por separado **cuenta el mismo riesgo dos veces**. **(3) Construcción defendible de una tasa libre de riesgo en COP, evitando el doble conteo**: la relación principal es la **paridad de tasas de interés (relación tipo Fisher)**, no una aproximación aditiva: `(1 + Rf_COP) = (1 + Rf_USD) × (1 + inflación esperada COP) / (1 + inflación esperada USD)`, donde `Rf_USD` ya se limpia del riesgo de default de EE.UU. (Treasury 10Y menos el spread de default de EE.UU.). La forma **aditiva** —`Rf_COP ≈ Rf_USD + (inflación COP − inflación USD)`— es únicamente una **aproximación de primer orden** de la relación de Fisher, válida cuando los diferenciales de inflación son pequeños, y debe presentarse como tal, no como el método en sí; con un diferencial de inflación COP-USD grande (como el vigente en Colombia en 2026, ver nota de datos abajo), la forma aditiva puede desviarse de la forma multiplicativa correcta de forma no despreciable. El riesgo soberano colombiano específico se incorpora **una sola vez**, como prima de riesgo país (CRP) dentro del costo de equity — no dentro de la tasa libre de riesgo. **(4) Exposición de la empresa al riesgo país**: no toda empresa domiciliada en Colombia tiene la misma exposición al riesgo país — depende de dónde genera sus ingresos reales, no de dónde está domiciliada. El método de Damodaran ("lambda") escala la prima de riesgo país por la proporción de ingresos que la empresa genera en el país, relativa al promedio de mercado: `λ = (% ingresos domésticos de la empresa) / (% ingresos domésticos de la empresa promedio del mercado)`. |
| Fundamento | Descontar flujos nominales COP con una tasa construida sobre riesgo soberano USD sin ajuste, contar el riesgo soberano colombiano dos veces, o usar una aproximación aditiva como si fuera la relación exacta cuando el diferencial de inflación es grande, desplazan el WACC y por tanto el Enterprise Value de forma sistemática — este es exactamente el gap que `02-methodology-reconciliation.md` tema 10 identificó como no discutido en ningún documento previo. |
| Fuente | Aswath Damodaran / NYU Stern: **(a)** relación de paridad de tasas de interés (Fisher) para construir tasas libres de riesgo en moneda local a partir de un risk-free en otra moneda y el diferencial de inflación esperada — tratamiento estándar de estimación de riskfree rates en distintas monedas; la forma aditiva como aproximación de la relación multiplicativa es la simplificación docente habitual, no la formulación exacta. **(b)** Measuring Company Exposure to Country Risk (`pages.stern.nyu.edu/~adamodar/New_Home_Page/valquestions/CountryRisk.htm`, consultado 2026-08-31): `λ = %ingresos domésticos (empresa) / %ingresos domésticos (empresa promedio del mercado)`. Estos dos puntos son **metodología**, independiente de la fecha de consulta. |
| Alternativas consideradas | (a) Mantener risk-free USD (Treasury) + ERP "Emerging Markets" genérico sin CRP explícito, aplicado a flujos COP sin ajuste (comportamiento actual, `financial-methodology.ts`) — rechazada: no resuelve la inconsistencia moneda/inflación. (b) Usar el rendimiento TES colombiano completo como risk-free COP, sin ajuste — rechazada como default: dobla el conteo del riesgo soberano si luego se suma un CRP adicional; sigue siendo válida solo si se documenta explícitamente que NO se suma ningún CRP después. Presentar la forma aditiva como *el* método (en vez de como aproximación) sería impreciso cuando el diferencial de inflación es grande, como es el caso actual COP-USD. |
| Implicación para código futuro | **Alcance**: aplicar esta metodología al caso Alpina (calcular `Rf_COP` vía Fisher, separar ERP maduro de CRP, aplicar lambda) **`can be handled manually/through existing structures`** — el cálculo se hace en el análisis del caso y se alimenta como un valor ya aceptado por los campos existentes de `financial-methodology.ts`/inputs del motor, sin requerir separar campos nuevos de risk-free/CRP/lambda en el esquema todavía. ### P-06 — Working capital operativo (Operating / Non-cash Working Capital)

| Campo | Contenido |
|---|---|
| Decisión | Se cierra la definición general: **Non-cash (Operating) Working Capital = (Activos corrientes operativos, excluyendo caja y valores negociables) − (Pasivos corrientes operativos, excluyendo deuda financiera con intereses)**. Específicamente: **incluir** cuentas por cobrar comerciales (AR), inventario, otros activos corrientes operativos, cuentas por pagar comerciales (AP) y otros pasivos corrientes acumulados/operativos (accrued operating liabilities). **Excluir caja y valores negociables** — no son necesarios para la operación diaria si están generando un retorno de mercado razonable, se gestionan como parte de la decisión de tesorería/inversión, no como capital de trabajo operativo, y ya se tratan por separado en el puente EV→Equity (tema 12/P-10); incluirlos en ΔNWC duplicaría su efecto. **Excluir deuda financiera con intereses (incluida la porción corriente de deuda de largo plazo)** — es una partida de financiamiento, no operativa; ya se refleja en el costo de capital (WACC) — incluirla en capital de trabajo sería "doble-contarla" (*double-dipping*, en los términos de la fuente citada). |
| Fundamento | Separar lo operativo de lo financiero evita contar dos veces el mismo efecto económico (una vez en la tasa de descuento/estructura de capital, otra en el flujo de caja operativo) y produce una medida de capital de trabajo que refleja únicamente el ciclo comercial del negocio (venta → cobro → pago a proveedores), que es lo que económicamente debería capturar el ΔNWC del FCFF. |
| Fuente | Aswath Damodaran / NYU Stern — definición estándar de *Non-cash Working Capital*, consultada 2026-08-31: "Non-cash Working Capital = Inventory + Other Current Assets + Accounts Receivable − Accounts Payable − Other Current Liabilities (Current assets excluding cash − Current liabilities excluding interest bearing debt)"; justificación explícita de exclusión de caja/valores negociables ("cash is not a wasting asset if it is invested to earn a fair market return") y de deuda con intereses ("he uses that portion of the debt when calculating the cost of capital, and counting it among working capital is double-dipping"). |
| Alternativas consideradas | (a) Mantener el ΔWC actual como % fijo de ingresos, sin composición explícita (comportamiento actual del motor canónico) — rechazada como principio general: no distingue qué cuentas debería incluir conceptualmente, aunque el valor % pueda seguir usándose como placeholder mientras no haya datos mejores. (b) Incluir caja operativa mínima (un "colchón" de caja necesario para operar) dentro del capital de trabajo, en vez de tratarla enteramente como no-operativa — variante reconocida en la práctica (algunas metodologías separan "caja operativa mínima" de "caja excedente"), pero no adoptada aquí como principio de cierre porque requiere un criterio adicional (cuánta caja es "mínima operativa") que Damodaran mismo resuelve tratando toda la caja como no-operativa por defecto, salvo ajuste explícito. (c) Definición Damodaran estándar (excluir caja/valores negociables y deuda con intereses) — **aceptada**. |
| Por qué se rechazaron las alternativas | (a) no es una decisión de composición, es la ausencia de una — necesaria como placeholder de cálculo, insuficiente como principio metodológico. (b) introduce un supuesto adicional (cuánta caja es "mínima operativa") sin evidencia de que Velarix lo necesite hoy; puede reconsiderarse caso por caso si la evidencia de Alpina lo justifica (ver P-06 nota abajo). |
| Cuentas ambiguas — explícitamente `CASE-SPECIFIC` | *Supplier finance / reverse factoring* y estructuras similares (financiamiento de cadena de suministro que técnicamente aparece como cuenta por pagar comercial pero funciona económicamente como financiamiento bancario) **no** se resuelven aquí de forma general — su clasificación depende de la sustancia económica del acuerdo específico (¿quién financia realmente, a qué tasa, con qué garantías?), no de su etiqueta contable. Esto es consistente con la nota de precaución del propio Caso 02 (Terpel) en `EXPEDIENTE-DE-VALORACION-V1.md`, que dejó esta pregunta explícitamente abierta tras el estudio de caso real — no se fuerza una respuesta general aquí tampoco. |

### P-07 — CAPEX y reinversión: el marco general

| Campo | Contenido |
|---|---|
| Decisión | Se cierra el marco conceptual, sin fijar un valor concreto de mantenimiento/crecimiento para ningún caso: **Reinversión = CAPEX neto + Δ Capital de Trabajo Operativo**, donde **CAPEX neto = CAPEX bruto − D&A** (la reinversión que excede simplemente reponer los activos que se deprecian). La relación económica fundamental que debe gobernar la coherencia entre crecimiento y reinversión es: **Crecimiento ≈ Tasa de Reinversión × Retorno sobre el Capital (ROC)** — es decir, `g ≈ Reinvestment Rate × ROC`. Para el valor terminal, esto implica que la **tasa de reinversión en estado estable debe ser exactamente `g / ROC`** — no un porcentaje de ingresos elegido independientemente del crecimiento y del retorno sobre el capital que la empresa genera. Un CAPEX/D&A/ΔWC proyectados sin verificar esta relación puede producir una combinación internamente inconsistente (ej. un crecimiento terminal alto financiado con una tasa de reinversión que, dado el ROC de la empresa, no podría sostenerlo). |
| Fundamento | Sin esta relación, es posible construir (sin darse cuenta) un valor terminal que asume crecimiento perpetuo sin la reinversión necesaria para sostenerlo — una de las formas más comunes de sobreestimar sistemáticamente un DCF. |
| Fuente | Aswath Damodaran / NYU Stern — fórmula fundamental de crecimiento estable: `g = Reinvestment Rate × Return on Capital`, y su inversa para el año terminal, `Reinvestment Rate (estable) = g / ROC`; definición de reinversión como `Net CapEx + Δ Non-cash Working Capital` — material de valoración estándar de Damodaran (Investment Valuation / notas de clase de DCF), consistente y verificado contra múltiples fuentes de su sitio durante esta investigación (2026-08-31). |
| Alternativas consideradas | (a) Mantener CAPEX/D&A/ΔWC como % de ingresos fijos e independientes entre sí (comportamiento actual) — rechazada como principio de cierre para el año terminal específicamente: no garantiza `Reinvestment Rate = g/ROC`, aunque puede seguir usándose como placeholder para el horizonte explícito mientras no haya un plan de inversión real del caso. (b) Exigir una regla universal de maintenance vs. growth CAPEX (ej. "CAPEX de mantenimiento = D&A siempre") — rechazada explícitamente por instrucción de este bloque: el monto exacto de mantenimiento/crecimiento de Alpina es case-specific, no una regla universal. (c) Cerrar la relación conceptual (`Reinvestment = Net CapEx + ΔWC`, `g ≈ Reinvestment Rate × ROC`, `Reinvestment Rate estable = g/ROC`) sin fijar montos — **aceptada**. |
| Por qué se rechazaron las alternativas | (a) es aceptable como placeholder de cálculo en el horizonte explícito, pero insuficiente en el año terminal, donde la coherencia interna del modelo (crecimiento perpetuo sostenible) depende directamente de esta relación. (b) fijaría prematuramente un supuesto que este mismo bloque pidió explícitamente no fijar. |
| Implicación para código futuro | `canonical-financial-engine.ts:216-223` (valor terminal) no verifica hoy ninguna relación entre `g`, CAPEX/D&A implícitos y un ROC calculado. ### P-08 — Normalización de EBITDA: procedimiento, no monto

| Campo | Contenido |
|---|---|
| Decisión | Se cierra el **procedimiento** para decidir si un ajuste de normalización de EBITDA es admisible, sin fijar ningún ajuste concreto para ningún caso. Un ajuste solo puede considerarse si satisface, como mínimo: **(1) Jerarquía de evidencia, no un formato único obligatorio** — el estándar es **evidencia suficiente y verificable, proporcional a la naturaleza y materialidad del ajuste**, no una lista fija de documentos exigidos por igual en todos los casos. Los estados financieros auditados y sus notas (cuando existen) constituyen, por sí solos, evidencia suficiente para muchos ajustes — no es necesario exigir además un contrato o factura individual si la nota a los estados financieros ya sustenta la partida y su monto de forma verificable. Documentación de soporte adicional (contratos, actas, comunicaciones internas) se exige **cuando esté disponible y cuando la materialidad o la naturaleza del ajuste lo amerite** (ej. un ajuste grande, una transacción con partes relacionadas, o una partida sin nota explicativa en los estados auditados) — no como requisito universal previo. Un ajuste sin estados financieros auditados y sin ningún otro soporte verificable no califica, independientemente de su monto. **(2) Clasificación recurring vs. genuinely non-recurring** — una partida "no recurrente" que de hecho ocurre todos los años (aunque con distinto monto o distinta etiqueta contable cada vez) no califica; requiere evidencia de que es genuinamente aislada, no un patrón recurrente disfrazado. **(3) Categorías reconocidas, cada una con su propio estándar de evidencia**: partidas no operativas (ingresos/gastos ajenos al giro del negocio); compensación a propietarios/familiares por encima o por debajo de mercado (requiere un benchmark de mercado defendible para la posición, no solo la afirmación de que "está sobrepagado/subpagado"); transacciones con partes relacionadas (requiere evidencia de que el precio/término difiere de condiciones de mercado, no solo que existe la relación); reestructuraciones; litigios; ganancias/pérdidas en disposición de activos; subsidios/ayudas gubernamentales inusuales; efecto cambiario; deterioros (impairments); y la distinción **clasificación contable vs. sustancia económica** (una partida puede estar contabilizada de una forma que no refleja su naturaleza económica real — el ajuste corrige la sustancia, no solo reclasifica la forma). **(4) NIIF 16 cuando afecte comparabilidad** — si se compara el EBITDA de la empresa contra comparables o períodos históricos bajo un régimen contable de arrendamientos distinto (pre/post-NIIF 16), debe documentarse explícitamente el efecto sobre EBITDA (NIIF 16 capitaliza arrendamientos operativos, elevando el EBITDA reportado al excluir el gasto de arrendamiento, que pasa a depreciación + interés) para no comparar cifras que no son metodológicamente equivalentes. **Cada ajuste admitido debe conservar, de forma auditable, tanto el valor original como el valor ajustado, con la evidencia y quién lo aprobó** — mismo patrón que ya exige la Decisión 2 (Bloque 1B-M) para overrides de estructura de capital. |
| Fundamento | Sin un procedimiento con estándar de evidencia explícito, la normalización de EBITDA se vuelve el punto más fácil de manipular una valoración (inflar el EBITDA "ajustando" partidas sin evidencia suficiente) — el procedimiento cerrado aquí no decide ningún ajuste, decide qué se necesita para que un ajuste sea admisible. Exigir un formato único (ej. siempre contrato/factura/acta) sin importar la materialidad o la disponibilidad real de soporte sería, en la práctica, tan poco realista como no exigir evidencia — muchos ajustes legítimos y bien sustentados solo tienen respaldo en los estados financieros auditados y sus notas, no en un documento transaccional individual. |
| Fuente | Consenso profesional de la práctica de valoración/M&A sobre normalización de EBITDA (categorías estándar: no recurrente, no operativo, compensación de propietario, partes relacionadas — ampliamente documentadas en la práctica de banca de inversión y valoración de empresas privadas); principio general de sustanciación de inputs de IVS 104 *Data and Inputs* (IVSC, vigente 31 enero 2025) aplicado específicamente a ajustes de normalización. No se identificó una única fuente primaria que codifique estas categorías como "estándar oficial" — es el consenso de la práctica profesional, tratado aquí como tal, no como un estándar IVSC numerado específico. |
| Alternativas consideradas | (a) Dejar la normalización de EBITDA completamente `OPEN`, sin ningún procedimiento, hasta el caso Alpina (postura del Bloque 2A) — rechazada por instrucción explícita de este bloque: el procedimiento general sí puede cerrarse ahora. (b) Fijar una lista cerrada de ajustes automáticamente permitidos, aplicables sin evidencia caso por caso — rechazada: repetiría el patrón "metodología uniforme aplicada sin comprensión del caso" que la reorientación de 2026-08-10 corrigió. (c) Exigir un formato de evidencia único y rígido (siempre contrato/factura/acta) para cualquier ajuste, sin importar su materialidad ni la disponibilidad real de soporte — rechazada explícitamente por instrucción de este bloque: es poco realista frente a cómo existe realmente la evidencia disponible (muchos ajustes solo tienen respaldo en estados auditados y sus notas) y confunde rigor con rigidez de formato. (d) Jerarquía de evidencia — suficiente y verificable, proporcional a naturaleza/materialidad, estados auditados como base suficiente cuando existen, soporte adicional cuando esté disponible y lo amerite — **aceptada**. |
| Por qué se rechazaron las alternativas | (a) confunde "no tenemos el monto todavía" con "no sabemos qué reglas aplicar para decidir un monto" — son preguntas distintas, y la segunda sí tiene respuesta general defendible. (b) elimina el juicio caso por caso que es precisamente el valor que Nicolás/Velarix aportan bajo el modelo expert-led. (c) impondría un requisito que en la práctica de valoración de empresas privadas rara vez se cumple documento por documento — arriesga rechazar ajustes bien sustentados por estados auditados solo porque no existe además un contrato individual. |
| Implicación para código futuro | Ninguna sobre el motor de cálculo (`canonical-financial-engine.ts` no decide ajustes, nunca debería). **Alcance**: la entidad `normalizations` del Expediente de Valoración (no implementada, `01-scope-surgery.md §3.2`) es **`NOT BUILDING`** para el caso Alpina — los ajustes de Alpina pueden documentarse manualmente (nota con evidencia adjunta, categoría, valor original/ajustado y aprobador, registrada en el propio Expediente del caso sin tabla nueva) sin requerir una entidad de base de datos formal; construir esa entidad solo se justificaría si el volumen de casos futuros lo amerita. |

### P-10 — Framework de EV → Equity bridge

| Campo | Contenido |
|---|---|
| Decisión | Se cierra el **marco de preguntas** que debe responderse para cada partida del puente Enterprise Value → Equity Value, sin diseñar todavía una taxonomía de tablas ni fijar tratamientos para ningún caso. Para cada partida, la pregunta metodológica es siempre la misma estructura: **¿es esta partida financiera (se resta/suma del EV) u operativa (ya está en el FCFF)? ¿está disponible económicamente para los accionistas, o su reconocimiento/control no implica disponibilidad real? ¿ya se contó su efecto en otro punto del modelo (FCFF, WACC, EBITDA), de forma que incluirla aquí también sería doble conteo?** Aplicado a cada partida: **Deuda financiera** — se resta (ya excluida del FCFF, reflejada en WACC). **Leases/obligaciones debt-like** — **no se afirma simplemente "lease liability = debt"**; el tratamiento correcto exige verificar primero la **consistencia entre cuatro elementos**: (i) si el EBITDA/EBIT usado es pre-NIIF 16 (incluye el gasto de arrendamiento como OPEX) o post-NIIF 16 (lo excluye, reemplazado por depreciación del activo por derecho de uso + interés del pasivo); (ii) la D&A del activo por derecho de uso (ROU) y si está incluida en la D&A total usada en el FCFF; (iii) los flujos de caja reales de arrendamiento (pagos de renta) y cómo se reflejan en CAPEX/financiamiento bajo NIIF 16; (iv) si el FCFF ya excluye el componente de interés del pasivo por arrendamiento de forma consistente con excluirlo también del puente. Solo después de verificar esa consistencia se decide si el pasivo por arrendamiento se trata como debt-like en el puente — tratarlo como deuda sin verificar que el EBITDA/FCFF ya lo excluyó de forma coherente puede penalizar el Equity Value dos veces (una en el FCFF más bajo por la D&A/interés del ROU, otra al restar el pasivo completo en el puente) o, en la dirección opuesta, dejar el efecto sin contar en ningún lado. **Caja** — se suma, pero distinguiendo **caja disponible** de **caja restringida** (garantías, depósitos regulatorios, efectivo comprometido contractualmente) — solo la caja genuinamente disponible para los accionistas debe sumarse sin ajuste; la caja restringida requiere evaluar si es un activo no operativo separado o si simplemente no debe sumarse al puente. **Exceso de caja vs. caja operativa** — relacionado con P-06: si se decidiera tratar parte de la caja como "operativa" dentro del ΔWC (variante no adoptada por defecto en P-06), esa porción no debe sumarse también en el puente EV→Equity (doble conteo). **Inversiones/activos no operacionales** — se suman al Equity Value a su valor de mercado/razonable si no están generando el FCFF que se está valorando. **Asociadas/negocios conjuntos (equity method)** — **no se asume que el carrying value bajo el método de participación (equity method) equivale al valor económico/de mercado de la asociada**: el equity method refleja la participación proporcional en el patrimonio contable histórico de la asociada, que puede diverger sustancialmente de su valor económico real (activos revaluados, expectativas de crecimiento no capturadas en libros, etc.). Si la participación es material para el Equity Value total, debe valorarse **separadamente con una metodología coherente** (un DCF o múltiplos propios de esa asociada, no simplemente sumar su book value); usar el carrying value como proxy solo es aceptable cuando se justifica explícitamente por qué la diferencia con el valor económico no es material para el caso, no por defecto. **Intereses minoritarios (NCI)** — si el FCFF se deriva de estados financieros consolidados al 100% (que incluyen la porción de subsidiarias no poseída), el valor atribuible a minoritarios debe restarse del Equity Value — de lo contrario se atribuiría a los accionistas de la matriz un valor que económicamente no les pertenece. **Pensiones u otras obligaciones debt-like** — se evalúan con la misma disciplina de consistencia que los leases (verificar dónde ya está su efecto en el FCFF/EBITDA antes de tratarlas como deuda en el puente), cuando son materiales. |
| Fundamento | El riesgo central en todo puente EV→Equity no es "olvidar" una partida, es **contarla en el lugar equivocado o contarla dos veces** — la disciplina correcta es siempre preguntar dónde más pudo haber entrado ya el efecto de esa partida (FCFF, WACC, EBITDA) antes de decidir cómo tratarla en el puente. Esto aplica con la misma fuerza a leases (consistencia EBITDA/D&A/flujo/puente) y a asociadas (carrying value ≠ valor económico salvo que se justifique) — ninguna de las dos admite una regla de una sola línea sin verificación. |
| Fuente | IFRS Foundation — IFRS 16 *Leases* (`ifrs.org/issued-standards/list-of-standards/ifrs-16-leases/`, consultado 2026-08-31): vigente desde períodos anuales que comienzan el o después del 1 de enero de 2019; exige reconocer activo por derecho de uso y pasivo por arrendamiento para prácticamente todos los arrendamientos, remplazando IAS 17 — la norma en sí no dicta cómo tratar el pasivo en un puente EV→Equity, solo establece el reconocimiento contable que hace necesaria la verificación de consistencia descrita arriba. IFRS Foundation — tratamiento general de inversiones en asociadas bajo el método de participación (equity method, IAS 28): el carrying value refleja participación en patrimonio contable histórico, no una medición a valor razonable/económico por defecto — base para no asumir equivalencia automática con valor económico. Evidencia interna extensa (`EXPEDIENTE-DE-VALORACION-V1.md §20-28`, 8 casos históricos: Ecopetrol/ISA/Bancolombia/Goldman Sachs/Munich Re) para NCI, associates, caja restringida (Candidato F, "disponibilidad económica de recursos") — el marco de preguntas cerrado aquí es la síntesis metodológica de esa evidencia, no una tabla de tratamientos por caso (que sigue `TRUE OPEN`, ver abajo). |
| Alternativas consideradas | (a) Diseñar ya una taxonomía completa de tablas/campos para NCI, leases, caja restringida, asociadas (`case_perimeter` u otra estructura) — rechazada explícitamente por instrucción de este bloque y consistente con la conclusión de los 8 casos históricos del Expediente. (b) Dejar el tema completo `OPEN` sin ningún marco, como quedó en el Bloque 2A — rechazada por instrucción de este bloque. (c) Tratar mecánicamente "lease liability = debt" y "carrying value de asociada = valor económico" como reglas de una línea — rechazada explícitamente por instrucción de este bloque: ambas ocultan verificaciones de consistencia necesarias (leases) o de materialidad/metodología propia (asociadas). (d) Cerrar el marco de preguntas exigiendo verificación de consistencia explícita para leases y valoración separada justificada para asociadas materiales, sin tabla de datos — **aceptada**. |
| Por qué se rechazaron las alternativas | (a) repetiría exactamente lo que los 8 casos históricos ya evitaron hacer. (b) desaprovecha el hecho real de que sí existe un principio general aplicable (evitar doble conteo). (c) sustituiría el análisis de consistencia por una regla de una línea en dos de las partidas más propensas a doble conteo real (leases, asociadas) — exactamente lo que este bloque pidió corregir. |
| Implicación para código futuro | `capital-structure.ts:63` (`netDebt = totalDebt − cash`, sin distinguir caja restringida, sin leases, sin NCI, sin asociadas) — el puente simple actual no tiene ningún campo para estas partidas. **Alcance**: si la evidencia de Alpina (C-08) muestra que tiene leases materiales, NCI, o participaciones en asociadas, aplicar el marco de verificación de consistencia **`can be handled manually/through existing structures`** — el análisis (verificar EBITDA pre/post-NIIF16, valorar la asociada por separado si es material) se hace fuera del motor y se aplica como ajuste documentado del caso. ### P-11 — DLOM y size premium: condicionales, no automáticos

| Campo | Contenido |
|---|---|
| Decisión | Se cierra el principio: **ni el DLOM (descuento por falta de liquidez de mercado) ni el size premium son ajustes obligatorios por el solo hecho de que la empresa sea privada.** Ambos son **condicionales**, y es metodológicamente válido concluir explícitamente `DLOM = no aplicable` o `no adjustment` si esa conclusión está justificada. Para el DLOM, la pregunta de cierre (consistente con IVS 105/200) es: **¿el interés que se está valorando (subject interest) es no comercializable, y los pasos previos de la valoración ya asumieron implícitamente un valor comercializable (marketable value) como punto de partida?** El DLOM es apropiado únicamente si ambas condiciones se cumplen — no es apropiado si el proceso de valoración ya incorporó la falta de comercialización en algún paso anterior (lo cual evitaría el doble conteo). Adicionalmente, un DCF (income approach) valora directamente el interés económico proyectado de la empresa — no necesariamente parte de un "valor comercializable" derivado de múltiplos de mercado público, a diferencia de un enfoque de mercado (comparables cotizados) — por lo que la aplicabilidad de un DLOM a un resultado de DCF depende de cómo se construyó ese DCF (¿el WACC/comparables usados ya reflejan liquidez de mercado público?), no es automática solo por tratarse de un DCF. Factores a evaluar caso por caso, ninguno decide por sí solo: **subject interest** (participación de control vs. bloque minoritario), **basis of value**, **perspectiva del comprador** cuando corresponda, **comercialización real de activos subyacentes**, **tamaño/bloque de la participación**, **liquidez de los activos de la empresa**, **salud financiera**. Para el **size premium**: tampoco es un ajuste por defecto — la literatura de tamaño (históricamente basada en estudios de deciles de mercados desarrollados, principalmente EE.UU.) tiene cuestionamientos empíricos serios sobre su persistencia y robustez en años recientes; aplicarlo requiere justificación explícita del caso, no una prima estándar. **En ambos casos, es obligatorio verificar el riesgo de doble conteo, pero solo contra ajustes que efectivamente ya se hayan incorporado en otra parte del modelo — no se asume que riesgo país (CRP) e iliquidez (DLOM) sean el mismo riesgo.** Son conceptos económicamente distintos: el CRP compensa el riesgo de operar en una economía/mercado de capitales específico (afecta a cualquier activo expuesto a ese país, cotizado o no); el DLOM compensa la falta de un mercado líquido para transar el interés específico que se valora (puede existir incluso para un activo sin ningún riesgo país adicional, ej. una participación minoritaria no comercializable en un país de riesgo bajo, y puede estar ausente en un activo con riesgo país alto pero perfectamente líquido). Tratarlos como intercambiables, o asumir que uno "ya cubre" al otro por defecto, sería tan poco riguroso como aplicarlos ambos sin verificación. La verificación de solapamiento debe hacerse **partida por ajuste realmente aplicado**: si el WACC del caso ya incorpora un CRP (P-05) y/o un lambda de exposición, revisar específicamente si ese ajuste ya refleja algún componente de iliquidez de mercado de capitales (no de la participación específica) antes de decidir si un DLOM adicional sería redundante — no descartar el DLOM solo porque existe un CRP, ni asumir que no hay solapamiento sin revisarlo. |
| Fundamento | Aplicar DLOM/size premium automáticamente "porque es una empresa privada" es una regla mecánica sin verificación de si las condiciones que justifican el ajuste realmente se cumplen — exactamente el tipo de metodología uniforme que v5.0 rechaza. |
| Fuente | IVSC — IVS 105 *Valuation Approaches and Methods* (`ivsc.org/wp-content/uploads/2021/10/IVS105ValuationApproaches.pdf`) e IVS 200 *Business and Business Interests*, consultados/verificados vía búsqueda dirigida 2026-08-31: "DLOM is appropriate when the subject interest is non-marketable, yet the prior steps in the valuation process result in a marketable value... DLOM is not appropriate if the prior valuation process has already taken marketability concerns into consideration"; IVS 200 exige consistencia entre el tipo de flujo de caja y la tasa de descuento, y trata explícitamente ajustes de marketability y de participación controladora/no controladora como parte del mismo marco. |
| Alternativas consideradas | (a) Aplicar un DLOM estándar (ej. 15-35%, rango de mercado citado en la práctica de EE.UU.) por defecto a cualquier empresa privada — rechazada explícitamente por instrucción de este bloque. (b) Nunca aplicar DLOM/size premium, tratándolos como ajustes obsoletos — rechazada: sería igual de mecánico que (a) en la dirección opuesta, y contradice la propia norma IVS que reconoce su aplicabilidad condicional. (c) Marco condicional con pregunta de aplicabilidad explícita y verificación de doble conteo, permitiendo `no aplicable` como conclusión válida — **aceptada**. |

(b) ignora que existen casos legítimos donde el ajuste sí aplica (ej. una participación minoritaria genuinamente no comercializable, sin ningún mecanismo de salida) — descartarlo sin evaluación sería tan poco riguroso como aplicarlo sin evaluación. |

### P-13 — Timing: fecha de valoración y convención de descuento

| Campo | Contenido |
|---|---|
| Decisión | Se cierran cuatro principios generales: **(1)** Todo caso debe tener una **fecha de valoración (valuation date) explícita**, conceptualmente distinta del período contable base de los estados financieros usados — hoy el motor no distingue ambos conceptos. **(2)** Cuando la fecha de valoración no coincide con el cierre de un año fiscal completo, corresponde modelar un **stub period** (período parcial) para el primer tramo proyectado, en vez de tratar el primer año proyectado siempre como un año completo desde la fecha de valoración. **(3)** Entre la convención de fin de año (year-end) y la convención de mitad de año (mid-year), la **convención de mitad de año es la más defendible por defecto** para un negocio en operación continua, porque los flujos de caja de una empresa operando normalmente se generan a lo largo del año, no en un solo pago al cierre — la convención year-end subestima sistemáticamente el valor presente de flujos que en realidad se reciben antes del cierre de cada año. La convención year-end sigue siendo una alternativa simple y defendible si se documenta explícitamente como elección consciente, no el default silencioso. **(4)** La convención elegida para los años del horizonte explícito debe aplicarse **de forma consistente al valor terminal** — no mezclar mid-year en la proyección explícita con year-end en la capitalización del valor terminal, o viceversa. |
| Fundamento | La convención de timing tiene un efecto sistemático y no trivial (aunque generalmente menor que WACC/g) sobre el valor presente — dejarla implícita sin decisión consciente es un vacío metodológico, incluso si el efecto cuantitativo es secundario frente a otros supuestos de este documento. |
| Fuente | Práctica estándar de valoración DCF (tratamiento de mid-year convention como ajuste estándar para flujos de caja distribuidos a lo largo del año, ampliamente documentado en la práctica de valoración corporativa/M&A y consistente con el tratamiento general de timing en IVS 105 sobre selección de métodos e inputs). No se identificó una página específica de Damodaran dedicada exclusivamente a este punto durante la investigación de este bloque — se cita como práctica estándar de la disciplina, no como una fuente primaria única verificada línea por línea (a diferencia de P-03, P-05, P-06, P-07, P-10, P-11, que sí tienen cita primaria directa verificada). |
| Alternativas consideradas | (a) Mantener el comportamiento actual (year-end implícito, sin fecha de valoración explícita, sin stub period) — rechazada: dos de los tres elementos (fecha de valoración explícita, stub period) no tienen ninguna alternativa metodológica defendible a "no hacerlo" cuando corresponde: son requisitos de precisión, no elecciones entre alternativas legítimas. (b) Adoptar year-end como convención de cierre, documentada explícitamente en vez de implícita — alternativa legítima y más simple, no descartada, pero menos precisa que mid-year para una empresa operando normalmente. (c) Adoptar mid-year como default, year-end como alternativa documentada — **aceptada**. |
| Por qué se rechazaron las alternativas | (a) dos de sus tres omisiones (fecha de valoración, stub period) no son realmente "alternativas metodológicas" sino vacíos de precisión sin contrapartida defendible. |
| Implicación para código futuro | En una implementación general futura: (1) un campo `valuation_date` explícito en el Expediente/`structured_input`, distinto de `base_period`; (2) lógica de stub period; (3) `canonical-financial-engine.ts:158` cambiaría a `t−0.5` si se adopta mid-year convention. No se modifica código en este bloque. **Alcance**: fijar la fecha de valoración explícita de Alpina es **`required for Alpina`**, pero **`can be handled manually/through existing structures`** — se registra como dato del Expediente/documentación del caso sin requerir un campo de esquema nuevo. Adoptar mid-year convention en el cálculo real (cambio de fórmula del motor) es **`required for Alpina`** solo si se decide que year-end no es aceptable para este caso específico; de lo contrario, year-end documentado explícitamente es defendible y el cambio de fórmula queda **`NOT BUILDING`** por ahora. |
| Test financiero requerido | Cuando se implemente: test que confirme una fecha de valoración explícita distinta del período base, y que la convención de descuento (mid-year por defecto) se aplique de forma idéntica en los años del horizonte explícito y en la capitalización del valor terminal. |
| Pregunta de entrevista | "¿Cuál es exactamente la fecha de valoración de Alpina, y usan convención de mitad de año o de fin de año?" |
| Respuesta defendible de Nicolás | "La fecha de valoración es un campo explícito, distinto del período contable base; usamos convención de mitad de año por defecto porque refleja mejor cómo una empresa en operación genera caja durante el año, documentando cualquier excepción." — la fecha exacta de Alpina es case-specific (ver C-10). |

| Campo | Contenido |

## CAPA C — Preguntas verdaderamente abiertas

Solo permanecen aquí cuestiones donde **no existe todavía evidencia suficiente para cerrar siquiera el principio general**, o donde **existen alternativas metodológicas legítimas cuya elección depende necesariamente del caso** — no como refugio para no investigar un principio estándar.

**Nota de versión (v1.1)**: la v1.0 de este documento tenía 4 ítems `TRUE OPEN` (O-01 a O-04). Tras la revisión: **O-01 se cierra** — quedó reemplazado por el principio cerrado **P-14** (ver Capa A) porque la parte de la pregunta que realmente carecía de evidencia general (¿existe una prima "PyME colombiana" válida por categoría?) sí tenía respuesta de principio (no); la parte genuinamente case-specific (¿qué riesgo económico específico de Alpina, si alguno, amerita un ajuste?) se mueve a la Capa B como parte de C-11/C-09. **O-03 se reclasifica** como `NOT BUILDING / OUT OF SCOPE` (ver abajo) — no es que carezca de respuesta investigable, es que v5.0 tiene un solo caso activo (Alpina) y no va a construir arquitectura general para casos futuros hipotéticos; la pregunta podría reabrirse legítimamente si existieran varios casos reales, pero hoy no es una pregunta que Velarix necesite responder. Quedan **2** ítems genuinamente `TRUE OPEN` (O-02, ahora O-01; y O-04, ahora O-02) más **1** ítem `NOT BUILDING / OUT OF SCOPE` (O-03, renumerado).

### O-01 — Representación general de perímetro de consolidación / NCI / asociadas más allá del marco de preguntas (P-10)

**Por qué es genuinamente abierta**: los 8 casos históricos del Expediente (`EXPEDIENTE-DE-VALORACION-V1.md §20-28`) documentan, con evidencia real y creciente a lo largo de 8 empresas de economías radicalmente distintas, que el problema de perímetro (NCI, asociadas, negocios conjuntos, "candidatos" A-G) está "fuertemente demostrado" pero que **la evidencia sigue siendo insuficiente para diseñar una representación general** (`case_perimeter`) — esta es la conclusión explícita y repetida de cada uno de los 8 casos, no una omisión de este documento. El marco de preguntas de P-10 resuelve *qué preguntar* (incluida la verificación de consistencia de leases y la valoración separada de asociadas materiales), no *cómo estructurar la respuesta* de forma reutilizable entre casos. Permanece abierta hasta que existan suficientes casos reales (Alpina y posteriores) que revelen qué estructura de datos sería genuinamente general, no prematura.

### O-02 — Umbral de materialidad para decidir cuándo activar el marco de preguntas de P-10, P-08, P-11

**Principio parcialmente cerrado, umbral numérico abierto**: el principio cualitativo sí queda cerrado en esta revisión — **una partida es material cuando razonablemente podría cambiar una conclusión de la valoración, un input material del modelo, o el rango de valoración presentado** (no un umbral de "tamaño en sí mismo" desconectado de su efecto). Lo que permanece genuinamente abierto es el **umbral cuantitativo concreto** (¿a partir de qué % del Enterprise Value, o de qué variación del rango de valoración, una partida cruza ese umbral?) — ninguna fuente consultada en este bloque (IVSC, Damodaran, práctica profesional) resuelve un número único citable y universal para ese umbral; distintos marcos profesionales usan convenciones distintas (ej. un % fijo de EV, un % de la variación del rango de sensibilidad, un umbral absoluto). Fijar un número arbitrariamente ahora, sin un caso real que lo calibre, repetiría el error que este documento evita en otros temas. **El umbral cuantitativo concreto para Alpina es case-specific** (se calibra frente al Enterprise Value y al rango de sensibilidad reales del caso, aplicando el principio cualitativo ya cerrado).

### O-03 — Estructura de datos reutilizable para EV bridge/NCI/leases entre múltiples casos futuros — `NOT BUILDING / OUT OF SCOPE`

**Por qué queda fuera de alcance, no `TRUE OPEN`**: a diferencia de O-01/O-02, esta no es una pregunta sin evidencia suficiente para responderse — es una pregunta que **v5.0 no necesita responder todavía porque no aplica a su alcance actual**. Velarix v5.0 tiene **un solo caso activo (Alpina)**; construir una estructura de datos general (`case_perimeter` u otra) para servir a casos futuros hipotéticos sería exactamente la clase de infraestructura prematura que la instrucción de este bloque pide evitar ("no conviertas una decisión metodológica elegante en una feature automáticamente"). Si Alpina puede ejecutarse correctamente y con trazabilidad completa usando resolución manual/caso-específica (ver P-10, Capa B), no hay necesidad de construir nada general ahora. **Esta clasificación no es permanente** — si en el futuro existieran múltiples casos reales con el mismo patrón de perímetro/NCI/leases, la pregunta se reabriría legítimamente como una decisión de arquitectura de producto informada por evidencia real, no hipotética.
